# 五条典型输入的 lint 演示

以下为实际 CLI 输出。普通 lint 返回 0；使用 --strict 时，有提示则返回 1。

## 1. 把那个页面优化一下，弄好看点，差不多就行。

退出码：0

```text
发现 12 项可改进之处：

1. [建议补充] 存在模糊描述 (vague)
   命中：那个 / 优化一下 / 弄好看点 / 差不多
   为什么会让 Codex 误解：主观词没有可检查的含义，Codex 可能自行选择设计、规模或改动程度。
   建议怎么补：把“好看”换成具体排版要求，把“优化”换成指标及阈值，列全“等等”省略的内容。

2. [建议补充] 指代对象不明确 (reference)
   命中：那个
   为什么会让 Codex 误解：无法确定你指的文件、页面、版本或上一项，容易修改错误对象。
   建议怎么补：写出具体文件或组件名、版本，以及需要参考的材料。

3. [建议补充] 缺少明确目标 (goal)
   为什么会让 Codex 误解：缺少要交付的结果，过程动作可能被当成任务完成。
   建议怎么补：补充目标，例如“生成一份按类别汇总的库存报告”。

4. [建议补充] 缺少成功标准 (success)
   为什么会让 Codex 误解：无法判断何时完成，可能过早结束或不断扩大改动。
   建议怎么补：列出可验证的验收项、数量或阈值；例如“每项均带来源，测试全部通过”。

5. [建议补充] 缺少范围白名单 (scope)
   为什么会让 Codex 误解：Codex 可能顺手修改未授权文件，或扩大搜索与执行范围。
   建议怎么补：明确可读材料和可写目录，例如“只读取 input/，仅修改 output/ 下的报告”。

6. [建议补充] 缺少禁区 (forbidden)
   为什么会让 Codex 误解：仅说明要做什么，没有约束不能碰的文件、功能或外部系统。
   建议怎么补：补充禁区，例如“不得修改原始数据、依赖和其他目录；不要发布”。

7. [建议补充] 缺少输出位置和格式 (output)
   为什么会让 Codex 误解：可能只在聊天中描述结果，或保存到你找不到的位置。
   建议怎么补：写出交付位置及格式，例如“输出到 output/report.md，使用 Markdown 表格”。

8. [建议补充] 缺少真实数据约束 (data)
   为什么会让 Codex 误解：涉及数据、引用或测试结果时，可能用猜测或示例填补证据空缺。
   建议怎么补：补充“仅使用可核对的真实数据；不得编造；缺失标未知，示例明确标为示例”。

9. [建议补充] 缺少不确定时的处理方式 (uncertainty)
   为什么会让 Codex 误解：对象不明确、资料缺失时，可能把推断当事实继续执行。
   建议怎么补：写明“缺失标未知；影响目标或范围的问题先问，其他推断明确标注”。

10. [建议补充] 缺少停止条件 (stop)
   为什么会让 Codex 误解：遇到失败后可能重复执行、替换服务或扩大权限。
   建议怎么补：例如“命令非零退出、材料缺失或需要越界时暂停，报告原因，不自动重试或换付费服务”。

11. [建议补充] 缺少验证步骤 (verification)
   为什么会让 Codex 误解：仅有成品无法证明结果可用，也难以复核是否满足成功标准。
   建议怎么补：说明要运行哪些测试或检查，记录命令、退出码及结果；未验证必须说明。

12. [建议补充] 缺少完成标记 (completion)
   为什么会让 Codex 误解：难以区分任务已经验收、仍在处理中，还是只生成了计划。
   建议怎么补：规定结果摘要的位置；仅在验证通过后写“完成”，受阻时写明未完成和原因。
```

   为什么会让 Codex 误解：几个动作的依赖、顺序和验收混在一起，可能遗漏步骤或直接进入批量操作。
   建议怎么补：拆成编号步骤，每步列出产物和验收；需要确认或样例的地方设检查点。

9. [高风险] 危险动作未声明确认点 (danger)
   命中：deploy / send an email
   为什么会让 Codex 误解：删除、发布、支付、登录或外发消息可能产生不可撤回的影响。
   建议怎么补：对该动作写明“执行前列出对象和影响，等待我明确确认”；不需要的动作直接禁止。

10. [建议补充] 缺少真实数据约束 (data)
   为什么会让 Codex 误解：涉及数据、引用或测试结果时，可能用猜测或示例填补证据空缺。
   建议怎么补：补充“仅使用可核对的真实数据；不得编造；缺失标未知，示例明确标为示例”。

11. [建议补充] 缺少不确定时的处理方式 (uncertainty)
   为什么会让 Codex 误解：对象不明确、资料缺失时，可能把推断当事实继续执行。
   建议怎么补：写明“缺失标未知；影响目标或范围的问题先问，其他推断明确标注”。

12. [建议补充] 缺少停止条件 (stop)
   为什么会让 Codex 误解：遇到失败后可能重复执行、替换服务或扩大权限。
   建议怎么补：例如“命令非零退出、材料缺失或需要越界时暂停，报告原因，不自动重试或换付费服务”。

13. [建议补充] 缺少验证步骤 (verification)
   为什么会让 Codex 误解：仅有成品无法证明结果可用，也难以复核是否满足成功标准。
   建议怎么补：说明要运行哪些测试或检查，记录命令、退出码及结果；未验证必须说明。

14. [建议补充] 缺少完成标记 (completion)
   为什么会让 Codex 误解：难以区分任务已经验收、仍在处理中，还是只生成了计划。
   建议怎么补：规定结果摘要的位置；仅在验证通过后写“完成”，受阻时写明未完成和原因。
